# Local demo and operations runbook

## Prepare

Install Go 1.27.2, Node 26, pnpm 11, Docker, and Docker Compose. Copy `.env.example` to `.env`; supply the allowlisted 17-digit SteamID, a server-side Steam Web API key, and randomly generated email-action/session secrets. An OpenAI API key is optional: without it, deterministic ranking and template explanations remain available. Never paste credentials into issues, logs, screenshots, this file, or `catalog_seed.json`.

Steam OpenID does not override privacy. Before the first synchronization, open Steam, go to **Profile → Edit Profile → Privacy Settings**, set **My profile** and **Game details** to **Public**, and make sure individual games needed for the demo are not marked private. Save the settings, return to Next Game Crush, and choose **Проверить снова**. The profile and Game Details checks are required; wishlist and achievement access are optional. When an optional source is private or unavailable, the application shows it as unavailable/stale and retains the last successful snapshot instead of blocking the whole synchronization.

Set `APP_BASE_URL` to the origin actually open in the browser: the Go origin (`http://localhost:8080`) for Compose, or Vite (`http://localhost:5173`) for split development where `/api`, `/auth`, and `/actions` are proxied to Go. CSRF validation is exact-origin. If Steam cannot return to localhost, use a temporary HTTPS tunnel as `APP_BASE_URL` and keep it consistent for the whole login.

## Start and demo

For a visitor-facing read-only demo, first sign in as the allowlisted owner and complete a successful import. Then set `DEMO_MODE_ENABLED=1` and restart the app. The authorization screen gains a dark **Демо-режим** button beside Steam login. It opens the real saved owner profile with a banner at the top; controls remain visible to explain the product, but attempts to synchronize, correct preferences, react, set reminders, send a digest, or delete data are stopped in the UI and rejected by the server. Keep the flag disabled when public demo access is not intended.

1. Run `make dev` and wait for the Compose health checks.
2. Open `http://localhost:8080`, sign in through Steam, and confirm the account matches the allowlist.
3. Start synchronization. Watch stages for library, recent activity, wishlist, achievements, catalog, AI enrichment, profile, and recommendations. On the dashboard distinguish **Новая находка для вас / Ещё новые игры** from **Уже в вашем желаемом**; wishlist membership is presentation context and has zero ranking weight.
   Achievement completion is automatic, with no manual checkbox or correction control. An unlocked base-game ending or a historical 100% snapshot makes the game a durable completion signal; additional distinct endings increase it within a fixed cap. A short completed game therefore remains meaningful beside a long open-ended game. Completion wording is historical unless Steam also reports nonzero two-week minutes; lifetime hours and an old/unknown last-played date never justify “recent interest”.
4. Confirm an exact release appears on a calendar day while month, quarter, year, Coming Soon, and unknown releases stay in their named buckets. Exercise **Все / Новые для меня / В желаемом** together with precision and score filters; changing one filter must not reset the others or the selected month.
5. Check **Охват каталога**. “Каталог обновляется” and unavailable/stale copy mean the saved results are intentionally retained and coverage may be incomplete. With discovery disabled, the reviewed seed remains the bounded fallback. The application never claims the Steam catalog is complete.
6. Review the recommendation explanations before submitting feedback. Deterministic cards show one concrete list of up to two grounded reasons and the label **По вашим игровым данным**; AI cards show one summary, the label **AI-сводка по вашим игровым данным**, and an optional collapsed **На чём основано** section. A wishlist-only card shows the saved watchlist sentence once, while a card without concrete support uses neutral copy. Pick two games supported by different data and confirm they do not repeat the old generic top-three reasons or claim that the game “adds something new”. Then submit Like/Dislike with a reason and optional text. Acknowledge **Отзыв сохранён** first, then wait for the ranking diff. “Комментарий сохранён без изменения правил предпочтений” is a valid no-rule result. For a synthetic negative co-op example, verify an applied **Кооперативные игры** correction appears in the taste profile, use **Не учитывать**, wait for the second rebuild, and confirm the rule moves to inactive history rather than being deleted.
7. Open feedback from a calendar cell using the keyboard. Check that focus stays inside the dialog, Escape returns focus to the launcher, and the layout has no page-level horizontal overflow at 375 px. A broken cover must fall back to the deterministic initial while the server-provided canonical Steam link remains usable.
8. Send a test digest and inspect the one message at `http://localhost:8025`. Follow one signed feedback link, then replay it and confirm the idempotent “already saved” response.
9. Run synchronization again and confirm the workflow ID/records remain idempotent. If wishlist access is temporarily private or fails, confirm the saved wishlist cards remain visible with their unchanged last-success time and stale reason. A later successful empty wishlist must show ready/zero instead of stale.
10. Open Diagnostics. Check Steam/OpenAI/SMTP/job state, discovery aggregate counts, freshness, and active/inactive preference history. For recommendation rebuilds, confirm the explanation summary contains only aggregate AI, deterministic, neutral, and localized fallback counts—never game names, identifiers, prompts, raw errors, or provider bodies. Use deletion only if you intend to sign out and remove all imported user data.

Diagnostics expose fixed, sanitized error categories. They do not return job payloads, raw prompts, API keys, cookies, signing material, SteamID values, or upstream response bodies.

## Verification and troubleshooting

Run `make verify` before a demo. It uses fake upstreams and a dedicated `next_game_crush_e2e` database; it does not recreate the application database. `TEST_HARNESS_MODE` and `FIXTURE_AUTH_ENABLED` are test-only and must remain `0`/unset for real use. A configured fixture route is absent outside the explicit harness mode, and test upstream URL overrides are rejected at startup.

If synchronization is stale, inspect the source states and sanitized job error in Diagnostics. Check profile visibility and Steam rate limiting first. Achievement metadata normally comes from localized `GetPlayerAchievements`; a successful player snapshot with missing text triggers a per-game `GetSchemaForGame` fallback. Failure of that fallback still preserves valid unlock state and previous shared definitions. If OpenAI is disabled or unavailable, strict literal English completion/ending phrases are still classified locally and unresolved definitions remain explicitly unknown. Existing semantic generations and completion projections are never replaced by weaker failure-derived data. Diagnostics expose only aggregate stage/reason/count information—never SteamID, AppID, API achievement names, descriptions, raw prompts, payloads, or provider bodies.

To distinguish expected history from a recency bug, compare Steam's two-week activity with the profile wording: a completed game with zero two-week minutes may appear as a strong historical preference, but must not be described as current activity. A publisher adding achievements later may reduce the current ratio without revoking an already observed 100% completion. Multiple ending achievements can strengthen the completion signal; DLC, New Game+, difficulty, speedrun, chapter, and all-endings/meta achievements do not independently prove base-game completion. If OpenAI is disabled, rate-limited, unavailable, or returns invalid output, existing features/vectors remain and ranking falls back to specific deterministic evidence. For email ambiguity, inspect Mailpit before explicitly retrying; do not assume SMTP exactly-once delivery.

For a preference-correction review, apply normal migrations by starting the app, synchronize once so trusted Steam categories are projected, then submit explicit feedback. Saved feedback with no applied rule is not an error. If a rule is applied, inspect it through the authenticated profile/Diagnostics UI. A rebuild failure leaves the rule/workflow status retryable from the UI; retry status instead of submitting the feedback again. Disabling a rule is idempotent, pins the prior ranking version for its rebuild, and preserves immutable history. Never use fixture routes, fake IDs, or real feedback text in production troubleshooting commands.

For server-side synchronization diagnostics, follow the structured JSON output:

```bash
docker compose logs -f app
```

Start with a `sync_request` event and copy its `workflow_id`. Follow matching `job_attempt` events through `started`, optional `heartbeat`, and the terminal stage. Use `job_id` and `parent_job_id` to inspect nested work. Matching `sync_source` events show the start and finish of owned games, recent play, wishlist, and the aggregate achievement import. A `retry_scheduled` stage means the queue will retry; `dead` is terminal. Safe `reason` values distinguish timeouts, rate limiting, upstream availability, malformed responses, lease loss, persistence failure, and an otherwise bounded internal error.

These logs intentionally omit SteamID, user and AppID values, game/profile names, job payloads, worker and fencing identifiers, credentials, prompts, upstream bodies, and raw errors. Do not paste secrets or raw Steam/OpenAI responses into diagnostics when sharing logs.

`catalog_seed.json` is the manually reviewed fallback. Update its AppIDs and adjacent source/observed metadata together, then run `make verify`. Steam Search discovery is opt-in with `CATALOG_DISCOVERY_ENABLED=1`; its default window is 30 days before through 30 days after today, with popular feeds processed first. Released games rated Mixed or below are discarded, while the saved review summary remains available for admitted games. Keep cron/timezone, Store and AI hourly budgets, catalog concurrency, page size, page cap, and new-AppID cap within `.env.example` bounds.

The app container owns the scheduler and both worker lanes. Starting or restarting it with `docker compose up -d` is sufficient on a VPS—do not add a host crontab or a separate CI schedule. Daily Steam Search runs build the release window; the weekly low-priority `GetAppList` reconciliation resumes from a durable cursor and shares the AppDetails budget/reservation gate instead of restoring the retired hourly scanner. A restart catches up the latest durable occurrence, and duplicate pages, metadata reservations, and semantic AI identities are reused rather than processed again. A 429, malformed page, exhausted retry, or unavailable Store endpoint degrades diagnostics but retains last successful candidates and the seed fallback. Disable/re-enable discovery to stop/resume new work; do not delete catalog rows as a rollout shortcut.

## Cleanup

- Stop services: `make down`.
- Remove application data and volumes intentionally: `docker compose down -v`.
- Remove only imported user data while retaining the shared catalog: use the authenticated Diagnostics deletion action.

## Real-Steam limitations observed

A real-account smoke run was not performed because no Steam/OpenAI credentials were supplied to this workspace. Consequently there are no direct observations to claim for Steam login, private-profile behavior, live rate limiting, current Store date text, or live OpenAI responses. Automated verification uses deterministic local fakes and proves adapter contracts plus the fixture product loop; it does not prove third-party availability on a future demo day. Run the manual steps above with the allowlisted account before a real demo and record the observed privacy/API results without recording credentials.
