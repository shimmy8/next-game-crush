# День 35: Next Game Crush

## Краткое описание

Многопользовательский веб-сервис анализирует библиотеку Steam, время в играх,
достижения, недавнюю активность и wishlist пользователя. На основе этих сигналов
он составляет профиль игровых предпочтений, находит предстоящие релизы Steam,
оценивает их релевантность и показывает персональный календарь.

Пользователь может оценивать рекомендации с помощью `Нравится` и `Не нравится`,
а также при желании указывать причину оценки. Обратная связь изменяет профиль и
учитывается в следующих рекомендациях. Сервис отправляет еженедельный email-
дайджест, уведомления о приближении релиза и письма при изменении даты выхода.

Название сервиса: **Next Game Crush**.

Короткое позиционирование: персональный AI-календарь, который помогает найти
следующую игру, способную по-настоящему увлечь пользователя.

## Какую задачу решает сервис

В Steam трудно следить за всеми потенциально интересными релизами. Wishlist
показывает только игры, которые пользователь уже обнаружил самостоятельно, а
общие подборки не знают, во что он действительно играет и какие рекомендации
ранее отвергал.

Сервис должен отвечать на четыре практических вопроса:

1. Какие интересные мне игры скоро выходят?
2. Какие релизы из моего wishlist приближаются или были перенесены?
3. Почему конкретная игра рекомендована именно мне?
4. Как сделать будущие рекомендации точнее?

## Целевая аудитория

- пользователи Steam с большой библиотекой или wishlist;
- игроки, которые не следят постоянно за игровыми новостями;
- пользователи, желающие видеть календарь только релевантных им релизов;
- игроки, которым недостаточно рекомендаций без понятного объяснения.

## Зафиксированные продуктовые решения

- Название сервиса — **Next Game Crush**.
- Это многопользовательский веб-сервис.
- Первая версия работает только с экосистемой Steam.
- Единственный внешний источник игровых данных в первой версии — официальный
  Steam Web API.
- Владение профилем подтверждается через Steam OpenID; OpenID используется для
  идентификации пользователя, а не для доступа к закрытым данным.
- Сервис не обходит настройки приватности Steam: закрытые данные не
  импортируются.
- Основной результат — персональный календарь предстоящих релизов.
- Wishlist является важным явным сигналом интереса.
- Пользователь оценивает рекомендации через `Нравится` и `Не нравится`.
- Оценки должны влиять на последующие рекомендации.
- Причину отрицательной или положительной оценки можно указать дополнительно.
- Сервис отправляет еженедельный email-дайджест.
- Сервис отправляет отдельные письма о приближении релиза и изменении даты.
- Планируется полный продуктовый вариант; при реализации объём можно сокращать.

## Границы первой экосистемы

Сервис рекомендует только игры, представленные в Steam, и строит профиль на
данных, полученных через официальный Steam Web API. Релизы других магазинов и
платформ пока не учитываются.

Перед реализацией необходимо составить точную карту официальных endpoints,
ограничений и доступности библиотеки, времени в играх, достижений, wishlist и
каталога будущих релизов. Недоступность отдельного типа данных не должна ломать
весь продукт: профиль строится по имеющимся сигналам, а интерфейс явно
показывает неполноту данных.

Не используются:

- Steam-аккаунты-боты и добавление сервисного аккаунта в друзья;
- scraping страниц Steam и неофициальных внутренних endpoints;
- browser extensions для чтения авторизованной Steam-сессии;
- Steam cookies, session token, пароль или Steam Guard-коды пользователя;
- персональный Web API key пользователя;
- сторонние игровые каталоги и агрегаторы данных.

### Закрытые профили

Steam OpenID не предоставляет доступ к закрытой библиотеке и подтверждает
только SteamID. Если нужные разделы профиля недоступны через официальный API,
сервис:

1. Не пытается обойти приватность или получить данные альтернативным способом.
2. Объясняет, какие данные недоступны и как это влияет на рекомендации.
3. Предлагает пользователю временно открыть необходимые разделы профиля в
   настройках Steam и повторить синхронизацию.
4. После успешного импорта хранит разрешённый снимок данных согласно политике
   хранения и пользовательскому согласию.
5. Если профиль впоследствии закрыт, не обновляет снимок, помечает его как
   устаревший и не удаляет автоматически из-за одной неудачной синхронизации.
6. Позволяет удалить импортированные данные, отключить Steam-профиль или
   удалить аккаунт целиком.

Полностью приватный профиль и отдельные игры, отмеченные пользователем как
приватные, считаются недоступными. Режим `Только для друзей` не поддерживается
через сервисный аккаунт: первая версия не создаёт и не эксплуатирует
Steam-ботов.

## Полный пользовательский поток

### 1. Первый вход

1. Пользователь открывает лендинг.
2. Сервис кратко объясняет, какие данные используются и зачем.
3. Пользователь входит через Steam OpenID и подтверждает владение SteamID.
4. Сервис запрашивает email для дайджестов и подтверждает его.
5. Пользователь выбирает часовой пояс и параметры уведомлений.
6. Сервис проверяет доступность данных профиля.
7. Если часть данных закрыта, пользователь видит объяснение, инструкцию по
   временному изменению видимости и кнопку повторной синхронизации. Сервис не
   предлагает способы обхода настроек приватности.

### 2. Первичная синхронизация

Сервис загружает доступные данные:

- список игр в библиотеке;
- время, проведённое в каждой игре;
- недавнюю игровую активность;
- достижения и долю их выполнения;
- wishlist;
- жанры, теги и другие доступные метаданные игр;
- даты известных предстоящих релизов Steam.

Исходные данные нормализуются. Дубликаты и различные издания одной игры по
возможности связываются. Для каждой записи сохраняются источник и время
последнего обновления.

### 3. Построение профиля игрока

Профиль создаётся из нескольких групп сигналов.

#### Неявные положительные сигналы

- большое время в игре;
- регулярные возвращения к игре;
- недавняя активность;
- высокий прогресс достижений;
- несколько любимых игр с общими жанрами или механиками.

#### Слабые или неоднозначные сигналы

- игра куплена, но ни разу не запускалась;
- очень короткая игровая сессия;
- игра запускалась давно;
- игра получена в составе набора и могла не выбираться осознанно.

#### Явные сигналы

- нахождение игры в wishlist;
- `Нравится` у рекомендации;
- `Не нравится` у рекомендации;
- выбранная пользователем причина оценки;
- ручное исключение жанра, тега или конкретной серии.

Профиль должен содержать не только жанры, но и более содержательные признаки:

- предпочитаемые игровые механики;
- одиночная или многопользовательская игра;
- сюжетность;
- сложность;
- темп;
- продолжительность;
- сеттинг;
- кооперативность;
- отношение к раннему доступу;
- отношение к отдельным жанрам и тегам;
- признаки, по которым пользователь часто отклоняет рекомендации.

Профиль должен быть объяснимым и доступным для просмотра и корректировки.

### 4. Получение кандидатов на рекомендацию

В пул кандидатов попадают:

1. Предстоящие релизы из wishlist.
2. Игры, похожие на игры с сильными положительными сигналами.
3. Продолжения и связанные серии.
4. Игры, совпадающие с устойчивыми предпочтениями пользователя.
5. Новинки, которые расширяют интересы пользователя, но не противоречат его
   явным отрицательным сигналам.

Из пула исключаются или понижаются:

- уже выпущенные игры, если экран посвящён будущим релизам;
- игры, которые пользователь явно отклонил;
- скрытые пользователем жанры и теги;
- дубликаты и различные карточки одного продукта;
- релизы без достаточно надёжной информации о дате, если пользователь отключил
  показ неопределённых дат.

### 5. Ранжирование

Каждый кандидат получает вычисляемый score. Базовая модель может учитывать:

```text
recommendation_score =
    library_similarity
  + wishlist_affinity
  + series_affinity
  + tag_affinity
  + explicit_feedback_adjustment
  + novelty_bonus
  - negative_feedback_penalty
  - uncertainty_penalty
```

Точные веса должны быть конфигурируемыми и проверяться на реальной обратной
связи. Wishlist и прямые оценки пользователя имеют больший вес, чем косвенные
выводы по библиотеке.

LLM не должна самостоятельно вычислять финальный числовой рейтинг. Её задача —
извлекать и сопоставлять смысловые признаки, обобщать профиль и создавать
объяснение. Итоговое ранжирование должно оставаться воспроизводимым и
наблюдаемым.

### 6. Персональный календарь

Календарь показывает релизы по дням, неделям и месяцам. Для каждой игры видны:

- название;
- дата или окно релиза;
- отметка `В wishlist`;
- персональная оценка релевантности;
- краткое объяснение;
- степень уверенности;
- действия `Нравится`, `Не нравится`, `Скрыть`, `Напомнить`;
- состояние даты: точная, приблизительная, изменённая или неизвестная.

Фильтры:

- только wishlist;
- только рекомендации;
- минимальная релевантность;
- жанры и теги;
- точные или приблизительные даты;
- релизы текущей недели, месяца или квартала.

Если несколько интересных игр выходят в коротком интервале, сервис может
выделять «плотную неделю релизов», но не планирует игровое время пользователя.

### 7. Объяснение рекомендации

Каждая рекомендация отвечает на вопрос «Почему это показано мне?». Объяснение
должно ссылаться на реальные сигналы и не придумывать факты.

Пример:

> Игра рекомендована, потому что вы много играли в две сюжетные RPG с похожими
> тегами, добавили предыдущую игру студии в wishlist и положительно оценили две
> рекомендации с исследованием открытого мира.

Необходимо различать:

- факты: время в игре, wishlist, оценка;
- выводы: вероятная любовь к механике или сеттингу;
- неопределённость: недостаточно данных для уверенного объяснения.

### 8. Обратная связь

Пользователь может поставить `Нравится` или `Не нравится` в веб-интерфейсе и
непосредственно из email по персональной защищённой ссылке.

После оценки сервис предлагает необязательную причину:

- не мой жанр;
- не нравится сеттинг;
- не интересует мультиплеер;
- не интересует одиночная игра;
- слишком сложно;
- слишком продолжительно;
- не доверяю раннему доступу;
- уже знаю об этой игре;
- рекомендация хорошая, но не сейчас;
- другое.

Feedback loop:

```text
Рекомендация
    -> оценка пользователя
    -> запись исходного контекста рекомендации
    -> обновление явных предпочтений
    -> пересчёт профиля
    -> изменение будущего ранжирования
    -> измерение качества следующей подборки
```

Одна отрицательная оценка не должна полностью запрещать жанр. Для сильного
негативного правила нужны повторяющиеся оценки или явное ручное исключение.

### 9. Email-дайджест

Раз в неделю пользователь получает письмо с:

- главными релизами ближайших недель;
- играми из wishlist;
- новыми персональными рекомендациями;
- изменившимися датами;
- короткими объяснениями;
- кнопками `Нравится`, `Не нравится` и `Напомнить`.

Дайджест не должен повторять один и тот же набор без новой информации. Сервис
учитывает ранее отправленные рекомендации и реакции на них.

### 10. Событийные письма

Поддерживаемые события:

- приближение выбранного релиза;
- выход игры сегодня;
- перенос даты;
- появление точной даты вместо примерного окна;
- существенное изменение карточки релиза;
- новая игра, получившая очень высокий персональный score.

Пользователь управляет типами уведомлений, частотой и периодом тишины. Повторные
события должны дедуплицироваться.

## Роль AI

AI используется там, где правила и точные совпадения недостаточны:

1. Обобщает профиль игрока по разнородным поведенческим сигналам.
2. Выделяет смысловые характеристики игр из доступных описаний и метаданных.
3. Сопоставляет предпочтения пользователя с будущими релизами.
4. Объясняет рекомендации на основе конкретных доказательств.
5. Интерпретирует свободный текст причины оценки.
6. Помогает различать локальную неприязнь к одной игре и устойчивое
   предпочтение.
7. Формирует компактные персональные тексты для email-дайджеста.

AI не должна:

- придумывать даты релизов;
- отправлять письма без правил частоты и согласия пользователя;
- скрыто менять сильные пользовательские предпочтения после одной реакции;
- принимать финальный ranking без сохраняемых факторов;
- использовать недоступные или закрытые данные профиля;
- утверждать причину рекомендации без ссылки на реальные сигналы.

## Предлагаемый системный поток

```text
Steam-профиль

      v
Сервис синхронизации -----> Нормализованное хранилище
                                      |
Каталог релизов Steam ----------------+
                                      |
                                      v
                              Feature extraction
                                      |
                                      v
                               Профиль игрока
                                      |
                                      v
                              Candidate retrieval
                                      |
                                      v
                              Ranking и фильтрация
                                      |
                         +------------+------------+
                         |                         |
                         v                         v
                Веб-календарь              Email scheduler
                         |                         |
                         +------------+------------+
                                      |
                                      v
                              Feedback collector
                                      |
                                      v
                           Обновление предпочтений
```

## Компоненты

### Web application

- лендинг;
- вход и связывание Steam-профиля;
- onboarding;
- персональный календарь;
- карточка рекомендации;
- экран игрового профиля;
- история оценок;
- настройки email;
- управление данными и удаление аккаунта.

### Backend API

- пользователи и сессии;
- Steam-интеграция;
- календарь релизов;
- рекомендации;
- оценки;
- настройки уведомлений;
- защищённые email-действия;
- административная диагностика фоновых задач.

### Background workers

- первичная и периодическая синхронизация профилей;
- обновление каталога релизов;
- обнаружение изменений дат;
- пересчёт пользовательских профилей;
- генерация рекомендаций;
- еженедельные дайджесты;
- событийные письма;
- повтор задач с ограничениями и dead-letter обработкой.

### Recommendation engine

- извлечение признаков;
- хранение явных и неявных предпочтений;
- получение кандидатов;
- детерминированный scoring;
- корректировка по feedback;
- LLM-объяснение;
- версия алгоритма для каждой рекомендации.

### Data storage

Минимальные сущности:

- `users`;
- `steam_accounts`;
- `games`;
- `game_release_dates`;
- `user_games`;
- `wishlist_entries`;
- `user_preference_profiles`;
- `recommendations`;
- `recommendation_factors`;
- `feedback_events`;
- `notification_preferences`;
- `email_deliveries`;
- `sync_jobs`.

Для каждой рекомендации важно сохранить snapshot факторов и версию алгоритма.
Иначе невозможно объяснить старую рекомендацию и измерить улучшение системы.

## Изменение даты релиза

Дата должна храниться как история, а не перезаписываться без следа:

- предыдущее значение;
- новое значение;
- точность значения;
- время обнаружения;
- источник;
- был ли пользователь уведомлён.

Это позволяет отличить настоящий перенос от уточнения приблизительного окна и
не отправлять ложные уведомления.

## Надёжность и ошибки

- Повторная синхронизация не создаёт дубликаты.
- Временная недоступность источника не удаляет ранее полученные данные.
- Неудачная генерация AI-объяснения не блокирует показ рекомендации.
- Рекомендация без объяснения помечается как временно неполная.
- Email-задачи идемпотентны и не отправляют одно письмо дважды.
- Ссылки оценки из email имеют ограниченный срок и не открывают аккаунт.
- Все фоновые задачи имеют наблюдаемые статусы и безопасные retry.
- Устаревшие даты и профили явно маркируются временем последнего обновления.

## Приватность и пользовательский контроль

- Запрашивать только данные, необходимые для работы продукта.
- До подключения объяснять, что будет импортировано.
- Использовать Steam OpenID только для подтверждения SteamID и не представлять
  его пользователю как разрешение на чтение закрытого профиля.
- Не запрашивать пароль, Steam Guard-коды, cookies, session token или личный
  Web API key пользователя.
- Не использовать ботов-друзей, scraping или автоматизацию Steam-клиента для
  обхода настроек видимости.
- Не пытаться импортировать полностью приватные игры или другие данные, которые
  Steam Web API не возвращает текущему сервису.
- Не продавать и не публиковать игровой профиль.
- Позволить отключить отдельные типы персонализации.
- Позволить удалить оценки, Steam-связь и весь аккаунт.
- Не помещать чувствительные идентификаторы в LLM prompt без необходимости.
- По возможности передавать модели агрегированные признаки вместо полной
  истории пользователя.
- Хранить согласие на email и позволять отписаться одним действием.

## Метрики качества

Продуктовые:

- доля рекомендаций с `Нравится`;
- доля рекомендаций, добавленных в wishlist;
- открытия календаря;
- открытия email;
- клики по рекомендациям;
- отписки от уведомлений;
- доля повторяющихся или уже известных рекомендаций;
- изменение качества после накопления feedback.

Технические:

- свежесть каталога релизов;
- свежесть профиля пользователя;
- длительность синхронизации;
- процент неудачных фоновых задач;
- дубли email;
- стоимость AI на пользователя;
- доля объяснений, построенных без подтверждающих факторов.

Главный показатель первой версии: пользователь регулярно отмечает хотя бы одну
рекомендацию как интересную и не считает календарь шумным.

## Полный вариант и возможное сокращение

### Полный вариант

- многопользовательская авторизация;
- реальная синхронизация Steam;
- история библиотеки и wishlist;
- обновляемый каталог релизов;
- гибридная рекомендательная система;
- объяснения AI;
- feedback с причинами;
- календарь;
- еженедельный дайджест;
- событийные уведомления;
- обнаружение переносов;
- пользовательские настройки;
- измерение качества рекомендаций.

### Если потребуется сократить MVP

Порядок сокращения без разрушения идеи:

1. Убрать свободный текст причин, оставить готовые варианты.
2. Оставить только еженедельный дайджест без событийных писем.
3. Пересчитывать профиль пакетно, а не сразу после оценки.
4. Убрать достижения и использовать библиотеку, часы и wishlist.
5. Оставить один вид календаря — список по неделям.
6. Ограничить каталог ближайшими 90 днями.
7. Для демонстрации использовать небольшой заранее синхронизированный каталог,
   сохранив реальный пользовательский профиль и feedback loop.

Нельзя вырезать из демонстрационной версии:

- персонализацию по Steam-профилю;
- wishlist;
- будущие релизы;
- объяснение рекомендации;
- `Нравится` и `Не нравится`;
- влияние оценки на следующую подборку;
- хотя бы один реальный email-сценарий.

## Сценарий демонстрационного видео

1. Пользователь открывает сервис и подключает Steam-профиль.
2. Сервис показывает процесс синхронизации и краткий профиль интересов.
3. Пользователь открывает календарь ближайших релизов.
4. На экране одновременно видны игры из wishlist и новые рекомендации.
5. Пользователь открывает рекомендацию и видит объяснение с факторами.
6. Пользователь ставит `Не нравится` и выбирает причину.
7. Сервис пересчитывает подборку и показывает, что изменилось.
8. Пользователь ставит `Нравится` другой игре и включает напоминание.
9. Показывается тестовое изменение даты релиза.
10. Пользователь получает email с уведомлением или недельным дайджестом.
11. Из письма он оценивает рекомендацию без повторного входа.
12. В веб-интерфейсе появляется сохранённая оценка.

## Формулировка для сдачи

> Я решал задачу персонального отслеживания игровых релизов в Steam. Веб-сервис
> анализирует библиотеку пользователя, время в играх, достижения и wishlist,
> строит профиль предпочтений и формирует персональный календарь будущих
> релизов. AI сопоставляет смысловые характеристики игр с поведением
> пользователя и объясняет каждую рекомендацию. Пользователь оценивает
> рекомендации, а сервис учитывает обратную связь в следующих подборках.
> Еженедельный дайджест и событийные email-уведомления сообщают о подходящих
> релизах и переносах дат.

## Вопросы для OpenSpec proposal

Перед фиксацией архитектуры нужно исследовать и выбрать:

1. Какие официальные Steam Web API endpoints использовать для библиотеки,
   времени в играх, недавней активности, достижений, wishlist и каталога?
2. Какие из выбранных endpoints требуют публичного профиля или публичного
   раздела `Game details`?
3. Можно ли надёжно получать wishlist и будущие релизы только через
   официальный Steam Web API, и какие у этих данных ограничения?
4. Как часто разрешено и целесообразно синхронизировать данные с учётом лимитов
   Steam Web API?
5. Какой срок хранения назначить последнему успешно импортированному снимку,
   если профиль стал закрытым?
6. Как моделировать неточную дату: день, месяц, квартал, год, `coming soon`?
7. Какой стек будет использоваться для web, workers, базы и email?
8. Какой LLM и embedding-провайдер использовать?
9. Нужны ли embeddings уже в первой версии или достаточно тегов и правил?
10. Как измерять улучшение после feedback на небольшом количестве пользователей?
11. Нужно ли импортировать существующие пользовательские реакции из других
    источников?
12. Какой период будущих релизов показывать по умолчанию?

## Предлагаемая последовательность OpenSpec

Первый proposal лучше ограничить вертикальным срезом:

```text
один пользователь
  -> подключение реального Steam-профиля
  -> импорт библиотеки и wishlist
  -> небольшой каталог будущих релизов
  -> генерация и объяснение рекомендаций
  -> календарь
  -> feedback
  -> пересчёт
  -> одно email-уведомление
```

После работающего вертикального среза отдельными изменениями можно добавить
полную многопользовательскую эксплуатацию, историю переносов, продвинутую модель
ранжирования, еженедельные дайджесты и продуктовую аналитику.
